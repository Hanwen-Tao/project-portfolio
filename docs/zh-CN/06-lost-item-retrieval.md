## 一、摘要

一个帮失主在校园招领处的登记里找回失物的检索系统。失主手里有什么就用什么：照片、中文或英文描述、大概的遗失时间和地点。四条线索的分数（两条图像线索、一条跨模态线索、一条跨语言文字线索）先在每个查询内标准化，再加权融合，最后叠加时间地点先验。第二版加入了用 LoRA 微调的图像编码器和一个学习式置信度模型，并做成了三层的网页系统。

只用照片时，LoRA 微调把 Recall@1 在 5 折交叉验证中从 0.735 提到 **0.949**，在另一校区的外部测试中从 0.731 提到 **0.943**。基准数据是用 CO3D 物体视频构建的，不是真实的招领照片；这对这些数字意味着什么，见第三节。

## 二、问题

招领处登记每件拾获物时会拍一张照片、写一段简短描述，并记下拾获的时间和地点。失主之后来找时，可能有遗失前拍的照片，可能有描述，可能两者都有，也可能都没有，时间和地点也只是大概的范围。任务是给招领处里还没认领的登记排序，让失主的物品排在最前面。

它比单纯的以图搜图难在三处：

- **缺失的模态组合各不相同。** 融合方法要能处理任意一组线索，不能每种组合各训一个模型。
- **两张照片差别很大。** 招领处把物品放在桌上拍；失主的照片是使用中的样子，角度和光线都不同。
- **相似的东西很多。** 黑色背包、白色杯子、银色笔记本电脑都很常见，只看外观常常分不清，时间和地点要分担一部分判断。

## 三、基准数据及其局限

拿不到带真实配对的招领照片，所以两校基准用 **CO3D**（Reizenstein 等，ICCV 2021；CC BY-NC 4.0，仅限非商业用途）构建：

| | |
|---|---|
| 一件物品 | CO3D 里的一段物体视频 |
| 招领处照片 | 取一帧，按掩码抠出物体，贴到素色桌面背景上 |
| 失主照片 | 同一段视频里相隔较远的两帧，保留原场景 |
| 时间与地点 | 在真实的校园地点上模拟（OpenStreetMap） |
| 规模 | 成大 185 件（370 个查询）· 清大 106 件（212 个查询），10 个日常物品类别 |

**局限。** 招领处照片和失主照片出自同一段视频，属于合成配对，每份报告里都写明了这一点。微调编码器用的训练池（另外 2,920 个 CO3D 物体）经过检查，和基准没有任何重叠：构建训练池时排除了基准用到的 1,546 段视频。

招领处一侧的描述用本地的 Qwen3.5-4B（4 位量化）生成。失主一侧的描述计划由组员手写；在那之前，文字相关的实验用另一个视觉语言模型根据失主照片生成的模拟描述，并标明是模拟的。

## 四、技术路径：检索核心

```
失主查询（照片？描述？时间范围？地点？）
  │
  ├─ Grounding DINO 裁切 ──── 用描述里的类别词；没有描述时用通用提示词 "object"
  │
  ├─ 对每条未认领登记计算各线索分数
  │     img    DINOv2 图 ↔ 图                     （裁切后）
  │     img2   SigLIP 2 图像塔 图 ↔ 图             （裁切后；v2 换成 LoRA 微调版）
  │     cross  SigLIP 2 照片 ↔ 描述，两个方向取平均
  │     txt    BGE-M3 描述 ↔ 描述                 （中文 / 英文）
  │
  ├─ 每条线索在本查询内做 z-score 标准化 → 加权求和；缺少的线索从分子和分母中去掉
  │
  ├─ 时间地点先验：时间硬过滤（留 6 小时宽限）
  │                + 按距离和时间差指数衰减
  │
  └─ 排序结果，附每条线索的证据和一句白话理由
```

**为什么在每个查询内做 z-score。** 不同编码器的余弦相似度尺度不同；一张清晰照片的查询，分数分布也比一句含糊描述的查询拉得更开。把每条线索在本查询的整个图库上标准化，就能放到同一把尺子上比较，缺少的线索也能直接去掉。这需要本查询对整个图库的分数分布，所以检索是对图库精确计算，而不是近似最近邻（图库几百到几千条，NumPy 计算不到 10 毫秒）。

**调参方法。** 权重和先验参数在成大数据上用按物品分折的 5 折交叉验证选定。清大作为外部测试：参数在成大全量上定好后，只跑一次。对照组是 BM25 关键词检索，以及每条线索单独使用的结果。

**负面结果照样记录。** 局部特征重排序（SuperPoint + LightGlue）做了实现、缓存和交叉验证，没有带来提升，默认关闭。

## 五、两个自己训练的模型

### 模型 1：用 LoRA 微调的图像编码器

| | |
|---|---|
| 底座 | `google/siglip2-base-patch16-224`，只用视觉塔 |
| LoRA | r 16、α 32、dropout 0.1；池化头全量训练；可训练参数 9,741,312 个 |
| 损失 | 监督对比损失，τ = 0.05 |
| 批次 | 24 个物体 × 4 个视角；按（类别，颜色）分组装批，每个批次里都有外观相近的困难负样本 |
| 优化 | AdamW，学习率 1.5e-4，5% 预热，2,500 步，fp16，梯度检查点 |
| 硬件 | RTX 4070 笔记本显卡，8 GB 显存，用时 106.5 分钟 |
| 选模型 | 第 1,900 步开发集 MRR 最高（0.987；同样 299 个开发物体上，预训练编码器的 R@1 是 0.719） |

LoRA 只加在给外观线索用的视觉塔上。跨模态线索继续用原版 SigLIP 2，因为只微调一个塔会破坏它和文字塔的对齐。

### 模型 2：学习式置信度

对每个（查询，候选）生成一行特征：各线索的 z-score 和原始余弦、线索缺失标记、先验的时间项和地点项、候选在各线索下的名次，用逻辑回归建模。输出候选"是同一件"的概率，以及"这件东西可能还没被捡到"的分数。在成大上按物品分折做交叉验证：判断"不在库里"的 AUC 0.969，Brier 分数 0.003。概率只附加在结果上，不改变排序。

## 六、系统分层

```
┌──────────────────┐   REST，JWT    ┌──────────────────────────┐   HTTP    ┌────────────────────────────┐
│ 前端             │ ─────────────▶ │ 后端（FastAPI）          │ ────────▶ │ 模型服务（FastAPI）        │
│ React + TS，Vite │                │ 账号与角色               │  /embed   │ 无状态：Grounding DINO、   │
│ 手机优先，       │ ◀───────────── │ 拾获登记、遗失登记       │  /rerank  │ SigLIP 2（+LoRA）、DINOv2、│
│ 校园地图         │     照片       │ 打分 = 检索核心          │           │ BGE-M3、模型 2             │
└──────────────────┘                │ 自动比对、认领           │           └────────────────────────────┘
                                    └────────────┬─────────────┘
                                                 │ SQLAlchemy
                                         ┌───────▼────────┐
                                         │ PostgreSQL     │  （测试用 SQLite）
                                         │ + 照片存储卷   │
                                         └────────────────┘
```

| 决定 | 理由 |
|---|---|
| 模型服务无状态，后端是唯一的数据源 | 重启模型服务或更换 LoRA 权重都不会丢数据 |
| 线上打分直接复用离线评测的 NumPy 代码和同一份配置 | 报告里的数字就是演示系统的实际行为 |
| 每条向量都记录 `model_version` | 不同权重产生的向量不会混在一起算 |
| 提供不依赖 PyTorch 的玩具模型后端 | 前端、后端和 CI 都不用下载约 5 GB 的模型 |
| 上传照片时去掉 EXIF/GPS 信息 | 保护隐私 |

招领处登记新物品时，后端会把它和本校区所有未结案的遗失登记逐一比对；如果它进入某位失主的前 3 名且分数超过阈值，就通知这位失主。认领需要招领处人工审核。Docker Compose 一条命令启动四个容器（数据库、模型服务、后端、nginx 托管的前端）；CI 用玩具模型构建这四个容器，并跑端到端冒烟测试。

## 七、结果

### 主要对比（Recall@1）

| 条件 | 成大 5 折交叉验证，v1 → v2 | 清大外部测试，v1 → v2 |
|---|---|---|
| 只用照片 | 0.735 → **0.949** | 0.731 → **0.943** |
| 照片 + 时间地点 | 0.857 → **0.951** | 0.901 → **0.967** |
| 照片 + 模拟的失主描述 + 时间地点 | — → 0.992 | — → 0.981 |

v1 用预训练编码器；v2 换成 LoRA 微调的编码器。最后一行用的是模拟的失主描述（见第三节）。

### 期末阶段的实验

| 实验 | 结论 |
|---|---|
| **先验敏感度**：换其他规则重新模拟时间和地点 | 如果物品可能被带到校园任何地方，先验反而会误导（照片条件 0.940 → 0.866），所以部署配置把先验减半 |
| **加大检索库**：加入另一校区和训练池，最多 3,363 条 | 只用照片时成大 R@1 0.949 → 0.876；最后一步加入的是编码器训练用过的物品，结果偏乐观；只加没见过的物品（742 条）时 R@1 为 0.927 |
| **失败分析**：只用照片时排在第 5 名之后的 11 个查询，逐张人工检查 | 8 个是裁切框框到了背景物体，1 张失主照片几乎看不到物品，2 个是真正的外观判断错误 |
| **裁切图与整张图取平均**：看过这些失败案例后才想到的规则 | 在训练池留出的物体上 0.948 → 0.955（在噪声范围内），排在第 5 名之后的从 8 个降到 2 个。报告中写明是事后分析，**未部署** |
| **端到端**：把 582 个基准查询经 HTTP 发给运行中的系统 | 1,746 个"查询 × 条件"中有 1,745 个名次与离线评测完全相同（剩下的一个离线排第 77 名，超出了返回的 50 条）；新照片约 0.9 秒 |

## 八、测量纪律

- **原始产出冻结。** 报告中每张表背后的原始运行结果都存进了仓库，并附 SHA-256 校验值。核对脚本从保存的每个查询的名次重新计算 Recall@1 和 MRR，再和当次运行自己的摘要以及报告里写的数字逐一比对。
- **整体重跑。** 一个脚本用报告的参数重跑期末阶段的全部离线实验，18 个输出文件全部一致。
- **线上等于离线。** 部署的系统逐个查询和离线评测比对（见上节）；评审修改后再跑一次，两校共 2,328 个名次全部相同。
- **不在测试集上调参。** 按物品分折，清大只跑一次，事后想到的做法都明确标出。
- **测试。** 核心 44 项、后端 13 项、模型服务 6 项、前端 9 项，全部在不需要 GPU 的 CI 上运行。

## 九、局限与下一步

### 已知局限

- **合成配对。** 招领处照片和失主照片来自同一段 CO3D 视频。最主要的未决问题是这些结论在真实照片上是否成立。
- **元数据和描述是模拟的。** 时间地点是模拟的；手写的失主描述完成前，失主描述也是模拟的。先验敏感度实验说明了结果在多大程度上依赖模拟规则。
- **裁切是主要的失败来源。** 剩下的错误大多是在没有描述提供类别词时，检测器框到了背景物体。

### 下一步

- 小规模真实物品验证：拍 10–20 件真实物品，检验 CO3D 上的结论能否迁移。
- 组员为约 20 件物品手写失主描述，和模拟描述做对比。
- 更难的测试：检索库只留同类别、同颜色的相似物品。
